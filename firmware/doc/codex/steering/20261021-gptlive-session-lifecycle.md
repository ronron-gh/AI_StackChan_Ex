# GPT-Liveの操作に連動したセッション開始・終了

## 目的

GPT-Liveの音声セッションは無音・マイクミュート中も時間課金されるため、待機中にセッションを開始しない。画面タッチで会話を開始し、開始完了イベントと音声受付・画面表示を一致させる。今回は `store: false` とし、forkによる会話の引き継ぎは行わない。

## 対象範囲・主な変更ファイル

- `src/llm/ChatGPT/GPTLive.cpp` / `.h`: WebSocket接続とセッション状態を分離し、開始要求・終了要求・イベント・利用量を管理する。
- `src/llm/ChatGPT/GPTLiveFullDuplex.cpp` / `.h`: 全二重音声の開始・停止をセッション状態に連動させる。
- `src/mod/AiStackChan/RealtimeAiMod.cpp` / `.h`: 既存の録音開始・停止インターフェースを優先し、必要な場合だけタッチと表示の調整を行う。
- `doc/fw_design.md`、必要に応じて `doc/gptlive_full_duplex.md`: 状態遷移と操作仕様を既存の関連節に反映する。

主対象はCoreS3のGPT-Live全二重通信。共通のGPTLiveイベント処理を変更する際は半二重音声経路も整合させる。OpenAI Realtime、Gemini Live、TTS連携、I2S診断モードの既存動作は維持する。設定項目の追加は行わない。

## 現状

- `GPTLive.cpp` の `WStype_CONNECTED` で `session.start` を送信しており、画面タッチ前からセッションが動く。
- `session.started` では「Please touch」を表示し、タッチ後に録音を開始する。
- 全二重経路では停止時にWebSocketを直接切断するため、`session.closed` による終了確認と最終利用量の取得がない。

## 実装方針

### 状態と操作

| 状態 | 表示 | 処理・遷移 |
|---|---|---|
| 接続待ち | Connecting... | 接続完了で待機へ。自動ではセッションを開始しない。 |
| 接続済み・セッション未開始 | Please touch | タッチで開始要求を記録し、WebSocket処理タスクが `session.start` を一度だけ送信する。 |
| 開始待ち | Starting... | `session.started` を待つ。音声入力は送信しない。重複タッチは無視する。 |
| 会話中 | Listening... | 開始完了後に音声入出力を開始する。発話中の既存表示は維持する。再タッチで終了待ちへ。 |
| 終了待ち | Stopping... | 新規音声入力を止め、再生待ち音声を破棄して発話を停止する。`session.close` を一度送信し、イベント受信を継続する。重複タッチは無視する。 |
| 終了確定 | Please touch / Connecting... | `session.closed` の最終利用量を記録し、音声資源と接続を解放する。次回は新しい接続・セッションを使用する。 |

- `session.start` の `session.store` に `false` を明示する。ロール等の既存開始設定は維持し、以前のセッションIDを使ったforkや新たな履歴引き継ぎ処理は追加しない。
- WebSocket送受信と状態遷移はWebSocket処理タスクに集約し、UIからは要求だけを渡す。既存の開始・停止APIと録音状態参照が遷移中に矛盾しないようにする。
- 停止後の新規会話は新しいWebSocket接続を使う。同一接続上で `session.start` を繰り返す設計にはしない。
- 接続だけの待機をサーバーが切断した場合はセッション開始要求を発生させずに再接続する。接続前のタッチでは開始しない。
- 起動待ち・再接続・モード復帰による自動セッション開始は禁止する。会話中の通信断でも自動で新しい課金セッションを開始せず、再接続後に再タッチを待つ。

### 終了・異常処理

- `session.usage.updated` の `usage.seconds` は累積値として上書き保存し、加算しない。
- `session.closed` の `usage.seconds`、終了理由、セッションIDをログに残す。画面への料金表示や永続化は今回の対象外とする。
- 明示的停止では委譲中の処理完了を無期限に待たず、`session.close` の終了規則に従う。停止時にバックエンド処理が中断される場合があることを設計メモに記載する。
- 開始待ち・終了待ちにはそれぞれ有限のタイムアウトを設ける（初期値は各15秒を目安に実装時に定数化する）。開始タイムアウトや音声初期化失敗時も、開始済みの可能性があるセッションを放置せず終了・切断する。
- 終了イベント前の通信断やタイムアウトでは最終利用量を「未確定」として記録し、最後の累積値を確定値として扱わない。音声と接続を解放して操作可能な待機状態に戻す。
- モード切り替え時は、WebSocketタスクを休止する前に終了イベントを処理できる猶予を設ける。終了待ち中に先にタスクを止めることや、コールバック内で終了イベントを同期待ちすることを避ける。
- 音声停止・キュー破棄を冪等にし、前セッションの音声や遅延イベントが次の会話へ混入しないようにする。

## 設計上の注意点・副作用

- 接続完了後も、初回タッチから音声受付可能になるまで開始待ち時間が発生する。「Starting...」で受付前であることを示す。
- `store: false` は保存済み会話からのforkを利用しない指定であり、課金を止める指定ではない。課金時間の確認にはAPIの利用量を使う。
- 無操作での自動終了やローカルVADによる再開は今回追加しない。全二重通信は明示的停止まで継続する。
- I2Sドライバー、PSRAMバッファ容量、サンプルレート、音量処理は変更しない。

## 確認方法

- 起動後に待機させ、CONNECTEDだけでは `session.start` が送られないことをログで確認する。
- タッチにつき開始要求が一度だけ送られ、`session.started` 前には音声を送らないことを確認する。
- 開始・終了待ち中の連打でも二重開始・二重終了しないことを確認する。
- 再タッチで入力・出力が止まり、`session.close` → `session.closed` → 切断の順になり、最終利用量が一度だけ記録されることを確認する。
- 再開時に新しいセッションIDになり、前回の音声が流れないことを確認する。
- 開始失敗、音声初期化失敗、開始・終了タイムアウト、通信断、サーバー側終了、モード切り替えから操作可能な状態へ戻ることを確認する。
- `m5stack-cores3-realtime`、`m5stack-core2-realtime` をビルドする。キャッシュ済み依存を優先し、依存取得のためのネットワークが必要な場合は実行前に確認する。
- 実機/APIでの確認ができない項目は未確認として記録し、実測した扱いにしない。

## 戻し方

今回のセッション状態管理と表示変更だけを取り消し、接続時開始の従来処理に戻す。設定ファイルの移行は不要。ユーザーの既存差分は取り消さない。

## 実装・確認結果

- GPTLive共通処理に接続済み待機・開始待ち・会話中・終了待ちの状態管理を追加した。UIからはatomicな操作要求を渡し、送受信と状態遷移はWebSocketタスクで処理する。
- 開始はタッチ後、音声送信はsession.started後とし、store=falseを明示した。正常終了ではsession.closedの最終利用量と理由を記録してから接続を解放する。終了前の通信断・タイムアウトでは最終利用量未確定を記録する。
- 全二重経路と半二重経路で共通のセッション管理を使う。診断モードの単独音声動作は維持した。RealtimeAiModの既存APIで要求を渡せるため、同クラスの変更は不要だった。
- キャッシュ済み依存・ネットワーク無効のPlatformIOビルドで、m5stack-cores3-realtime、m5stack-core2-realtime、m5stack-cores3-realtime-aquestalkが成功した。ArduinoJson等の既存警告は残る。
- 開始・終了待ち中の重複操作、遅延した開始イベント、終了通知の重複、エラー・通信断、モード停止の経路をコード上で確認した。実機/APIによるイベント順序、タイムアウト・再接続、実際の課金時間の検証は未実施。
- 作業差分のgit diff --checkは問題なし。I2Sドライバー、設定値、UIタスクの構造は変更していない。
- 2026-10-22: ユーザーより実機での動作確認完了の報告を受けた。個別の異常系や実際の課金時間の検証結果は未報告。
