# GPTLive CoreS3 Full Duplex 検証

CoreS3内蔵のES7210／AW88298と共有I2Sクロックを直接扱う全二重実装。音声送受信とセッション管理はGPTLiveに統合し、半二重経路は削除した。統合後の全二重通信は実機確認済み。

## Function Calling

GPT-Liveのバックエンドから、日時取得、音量・明るさ変更、表情変更、タイマー、メモリ更新、および設定済みで接続に成功したMCPツールを呼び出せる。web_searchも引き続き利用する。関数処理は専用タスクで直列実行し、その間も音声送受信を継続する。音声入力を直接使うask／WakeWord関連関数は対象外。

関数処理中にタッチで停止した場合、未着手の処理と遅れて届いた結果は破棄する。すでに開始した操作は取り消せない。再開・モード切り替えの完了は実行中処理の終了を待つため、MCP等の通信時間に依存する。引数は4095 bytes、結果は8191 bytesまで。ツール名が衝突した場合は初期化エラーとし、シリアルログを確認する。

実機確認では、各関数の結果と実際の設定・動作の一致、MCP処理中の同時入出力、処理途中の停止・再接続を確認する。2026-10-25にユーザーよりFunction Calling追加後の動作確認完了の報告を受けた。個別の異常系試験の範囲は未報告。

GPT-Live用MCPクライアントでは応答待ちを30秒で打ち切る（接続・HTTP処理中はその通信待ち時間が加わる）。タイムアウト時の操作結果は未確定であり、自動再実行しない。

## ビルドと切替

    pio run -e m5stack-cores3-realtime
    pio run -e m5stack-cores3-realtime -t upload

AI ServiceはOpenAI GPT-Liveを選択する。GPTLIVE_FULL_DUPLEXが有効なこの環境でGPTLiveを生成する。CoreS3内蔵音声向けで、Core2／AtomS3R／外部Audio Module／REALTIME_API_WITH_TTSは対象外。WakeWordはこの環境では無効。

従来のOpenAI Realtime APIへ戻す場合は、platformio.iniの同環境の-DGPTLIVE_FULL_DUPLEXを無効にして次をビルド・書込みする。

    pio run -e m5stack-cores3-realtime -t upload

## 基本の確認

1. 音量は最初は64程度以下にして開始する。直接I2SではPCMに設定音量の二乗比を適用する。スピーカー音量0でもRXは継続する。
2. 接続が完了しPlease touchが表示されたら、従来の録音開始操作をする。タッチでセッションを開始してStarting...となり、session.started受信後に音声入出力とListening...表示を開始する。待機中はセッションを開始しない。ログに CoreS3 TX+RX started: 24000 Hz PCM16 mono, no AEC が出ることを確認する。
3. 約2秒ごとのログで RX / TX / Sent が増えることと、発話時に inLevel が変化することを確認する。
4. 応答を再生しているときに outLevel が変化し、その間も RX / Sent が増え続けることを確認する。TXには無音の継続送信も含まれるため、TXカウンタだけで応答の再生成功とは判断しない。
5. 録音停止操作で入出力を止める。Stopping...表示でsession.closeを送り、session.closedの最終利用量を記録してからWebSocketを切断する。停止前の応答を次回に持ち越さず、再接続後は再度操作して新しいセッションを開始する。
6. モード停止／復帰、切断再接続、音量変更、長い応答でも停止・再開できることを確認する。

全二重版には30秒の自動録音停止と、出力無音でのマイク切替を適用しない。手動停止までセッションの入出力を継続する。直接I2S所有中の効果音・アラーム音はスキップする。非TTSビルドなので既存の非同期TTSタスクは起動しない。別TTSのRobot::speechは無効で、Webの /speech APIは503を返す。

無音・ミュート中もセッション時間に応じて課金される。storeはfalseで、forkによる会話の引き継ぎは行わない。開始・終了待ちはそれぞれ15秒で打ち切り、終了イベント前の切断やタイムアウトでは最終利用量を未確定としてログに残す。開始・終了待ちの重複操作は無視する。

## ログの見方

- RX / TX / Sent: 開始後のサンプル累計。24 kHzなので約2秒あたり48000 sampleが目安。実際のWebSocket受信・送信待ちによりSentは遅れる場合がある。
- RXdrop: 入力キュー8窓（160 ms）が満杯で破棄した新着窓の数。ネットワーク送信が追いつかない場合に増える。
- TXempty: TXが再生リングからデータを取り出せず無音を送った窓の数。応答のないときも増える正常なカウンタであり、常に障害を意味する値ではない。
- queued: 再生待ちPCMのbyte数。512 KiBを超える入力が来るとセッションを停止・リセットする。
- inLevel / outLevel: 直近20 ms窓のPCMピーク。outLevelはソフトウェア音量適用後、DMAへ送る窓の値で、実際の再生とはDMAの待ち時間分ずれる。

## 任意のテスト音

直接I2Sだけの確認には、検証環境のbuild_flagsへ -DGPTLIVE_FULL_DUPLEX_TEST_TONE を一時的に追加して再ビルドする。この場合はWebSocket処理とAPI送信を行わず、画面のI2S test表示でタッチすると100 msの1 kHzテスト音を再生し、その間もRXを収集する。RX / TX / inLevel / outLevelを確認し、再タッチで停止する。Sentは出力しない。確認後はフラグを外して通常の会話検証へ進む。通常ビルドでは自動テスト音は無効。

## 現時点の制約

AEC／ノイズ抑制／再生中の送信マスクは実装していない。スピーカーをマイクが拾って自己応答する可能性がある。まず音量0で入力、次に小音量で同時動作を確認し、エコー処理は別途評価する。

共有クロックは24 kHzで固定し、ES7210／AW88298の初期化をM5Unifiedから直接I2Sへ引き継ぐ。画面・電源・I2CにはM5Unifiedを引き続き使用する。実機成功はビルド成功と区別する。
